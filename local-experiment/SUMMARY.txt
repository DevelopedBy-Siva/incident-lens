WHAT WAS BROKEN
================================================================================

evaluate.py used SERVICE-ONLY grouping:
  - Produced exactly 22 clusters (one per service)
  - Combined multiple unrelated incidents per service
  - Example: notification-worker had 49 logs in ONE cluster containing:
    * Kafka consumer lag (12 logs)
    * RabbitMQ queue backlog (10 logs)
    * Container crashes (various)
    * Normal heartbeats (multiple)

This made proper evaluation IMPOSSIBLE. We couldn't measure:
  - True incident detection (masked by mega-clusters)
  - Severity classification (one label for mixed incidents)
  - Precision/recall (no way to match ground truth)
  - Parse quality (unreliable metrics)

Previous results (13/22 valid JSON, ~48s latency) were UNRELIABLE.

================================================================================
WHAT WAS FIXED
================================================================================

1. Signature-Based Clustering (Production-Compatible)
   - Uses incident_clustering.py (MD5 hash of normalized error patterns)
   - 2-minute time window (matches production)
   - Merge-gap parameter (5min default) consolidates related incidents
   - Result: 28 incident candidates vs 22 service clusters

2. Multiple Incidents Per Service
   - notification-worker: 7 incidents (Kafka, RabbitMQ, heartbeats separated)
   - payment-api: 5 incidents (timeouts, pool exhaustion, retries separated)
   - order-service: 4 incidents (payment gateway, shipping, etc.)

3. Comprehensive JSON Parser (output_parser.py)
   - Handles 6 failure modes: success, partial, malformed, no_json, multiple_json, empty
   - Field-level completion tracking (severity, disposition, summary, etc.)
   - Validation (severity vocabulary, disposition values, confidence range)

4. Deterministic Ground Truth Matching (evaluation_metrics.py)
   - Temporal overlap calculation (Jaccard similarity)
   - Service-based filtering
   - Greedy best-match assignment
   - No LLM-based matching

5. Inference Latency Optimization
   - InferenceEngine class loads model ONCE
   - Reused across all predictions
   - Expected: <5s vs ~48s mean latency

6. Incident Candidate Generation
   - incident_candidates.jsonl for inspection
   - Shows: service, signature, duration, log_count, evidence, grouping_reason
   - Makes clustering debuggable

7. Validated Ground Truth
   - All 8 ground truth incidents verified against evaluation.log
   - Log counts match expected
   - Temporal boundaries correct
   - No overlaps

KEY INSIGHT
================================================================================

The old evaluation was measuring the EVALUATOR, not the MODEL.

With service-only grouping:
  - notification-worker (49 logs, mixed Kafka+RabbitMQ+heartbeats) → ONE prediction
  - Model forced to classify unrelated incidents with single label
  - No way to measure detection of multiple incidents
  - Metrics meaningless

With signature-based clustering:
  - notification-worker → 7 separate incidents
  - Model can classify each independently
  - True detection/classification capability measurable
  - Metrics reliable

THE NEXT RUN WILL BE THE FIRST VALID MEASUREMENT OF MODEL QUALITY.

Previous "poor results" were evaluation pipeline bugs, not necessarily model bugs.
